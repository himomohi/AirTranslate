## Findings

Critical: none.

High: none.

Medium: none.

Low / residual:

1. Distribution remains ad-hoc signed and not Apple-notarized. Current public wording discloses this in the README files, `docs/GETTING-STARTED.md`, and `Release/GITHUB-RELEASE-1.9.1.md`; this is a known distribution trust boundary rather than a new blocker.
2. User-chosen text/background color combinations can be low contrast. The release docs correctly avoid claiming arbitrary custom colors are accessibility-conformant; UI/accessibility evidence should record the checked combinations separately.
3. VoiceOver narration and new-user TCC inheritance are not proven by this source and artifact security review.
4. Remote post-upload asset verification remains a required publication follow-up. After GitHub Release upload, re-download each asset, compare bytes/SHA-256 to the local manifest, and repeat the artifact secret/sensitive filename/codesign spot checks before calling the remote release gate complete.

Final source re-review notes:

- Manual color entry only applies when `FloatingCaptionAppearance.nsColor(hex:)` accepts a 6-digit hex value; invalid drafts keep the Apply button disabled and are ignored by `apply()`.
- ColorPicker values pass through `FloatingCaptionAppearance.hexString(from:)`, which clamps extended RGB components before formatting.
- Floating-caption drag no longer relies on `NSWindow.performDrag`; it computes screen-space deltas and calls the same screen-bounds clamp as resize.
- Duplicate SwiftUI `WindowDragGesture` was removed from the caption view path reviewed here, leaving the AppKit drag surface as the movement owner.
- Final `ResizeHandle.draw` black-outline behavior does not add credential, network, file-write, or external-state risk.
- The final source and artifact review did not find a security defect requiring worker follow-up before publication.

Worker notification status:

- No concrete security defect was found that requires messaging `caption_implementation` before publication.
